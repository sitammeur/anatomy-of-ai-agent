Section 00·Setup

The model under the harness: Gemma 4

A harness is only as reliable as the model it drives. We use Google's open Gemma 4 through OpenRouter's free endpoint, with the plain OpenAI client.

setup§0
from openai import OpenAI

client = OpenAI(
    base_url="https://openrouter.ai/api/v1",
    api_key=os.environ["OPENROUTER_API_KEY"],
)

# override with MODEL=... in .env, no code changes
MODEL = os.environ.get("MODEL", "google/gemma-4-26b-a4b-it:free")

# no agent framework past this line

Part 1

From model to agent

Start with a bare model call. Add one layer at a time until it runs on its own.

Model→Scaffolding→Harness→Agent
Section 01·Model

The model is not the agent

Text in, text out, one response per prompt. Everything that makes it feel like an agent is code we write around it.

anatomy-of-ai-agent.ipynb§1
# One prompt in, one response out.
response = client.chat.completions.create(
    model=MODEL,
    messages=[{"role": "user", "content": "What's 17 * 24?"}],
)                                        # → 17 * 24 = 408

# A fresh call, no history included
messages=[{"role": "user", "content": "What number did I just ask you to compute?"}]
                                         # → "You haven't asked me to compute any numbers yet ..."

# Offer a tool schema: it can only DESCRIBE the call
response = client.chat.completions.create(model=MODEL, messages=..., tools=tools)
response.choices[0].message.tool_calls  # → get_weather({"city": "Paris"}). Nothing ran.

No memory

Each call is stateless. Unless we send the history back, it has none.

No loop

It answers once and stops. Nothing keeps it running.

No hands

It can express the intent to call a tool, but it can't act on it.

Outputs shown are from the saved notebook run. Anything that feels like memory in a chatbot is something we build.

Section 02·Scaffolding

Scaffolding is data, not a loop

The system prompt, the tool schemas, and the message list. It shapes how the model sees the world, but nothing here runs anything yet.

anatomy-of-ai-agent.ipynb§2
tools_schema = [{
    "type": "function",
    "function": {
        "name": "get_weather",
        "description": "Get current weather for a city. Pass forecast_days > 1 to also get "
                       "that many days of daily forecast, e.g. forecast_days=3 for a 3-day trip.",
        "parameters": {
            "type": "object",
            "properties": {
                "city": {"type": "string", "description": "City name, e.g. 'Tokyo'"},
                "forecast_days": {"type": "integer", "description": "How many days of forecast"},
            },
            "required": ["city"],
        },
    },
}, ...]                                  # + convert_currency

SYSTEM_PROMPT = "You are a helpful travel assistant with access to tools. ..."
AVAILABLE_TOOLS = {"get_weather": get_weather, "convert_currency": convert_currency}
messages = [{"role": "system", "content": SYSTEM_PROMPT}]

The schema is all it sees

The model never reads your Python. It only reads the name, description, and parameters.

Bad description, bad call

A vague description is the most common reason a model misuses a tool.

Name → function

AVAILABLE_TOOLS maps the string the model returns to the code that will run.

Section 03·Harness

The harness is what makes it run

It calls the model, runs the tools the model asked for, feeds the results back, and decides when the task is done.

anatomy-of-ai-agent.ipynb§3
def run_harness(messages, tools_schema, available_tools, max_turns=6):
    for turn in range(max_turns):
        response = client.chat.completions.create(
            model=MODEL, messages=messages, tools=tools_schema)
        msg = response.choices[0].message
        messages.append(msg.model_dump(exclude_unset=True))

        if not msg.tool_calls:            # stop: a plain-text answer
            return messages, msg.content

        for tool_call in msg.tool_calls:  # otherwise run every call
            fn_name = tool_call.function.name
            fn_args = json.loads(tool_call.function.arguments)
            result = available_tools[fn_name](**fn_args)
            messages.append({"role": "tool", "tool_call_id": tool_call.id,
                             "name": fn_name, "content": str(result)})

    return messages, "[Stopped: max turns reached without a final answer]"
Call the model
↓
Any tool_calls?
no
Return the text
yes
Run each tool in Python
↓
Append a "tool" message
↺ loop again
max_turns is the safety stop

The notebook also wraps the tool call in try/except. That one line matters in section 07.

Section 05·Context engineering

Deciding what enters the window

The model only knows what is in this call's messages. Memory is a choice about what to put there.

SHORT-TERM

self.messages, inside one run

A second agent.run() sees the first: "You just asked about Bengaluru." A new Agent sees nothing: "You haven't asked about a city in our current conversation yet."

LONG-TERM

Stored outside, injected back in

Facts live in long_term_memory.json. Before the run, we load them and add them to the system prompt. A fresh agent now answers: "Your favorite city is Tokyo…"

anatomy-of-ai-agent.ipynb§5
def save_memory(fact: str):
    facts = load_memory()
    facts.append(fact)
    with open(MEMORY_FILE, "w") as f:
        json.dump(facts, f)

system_prompt_with_memory = (SYSTEM_PROMPT + "\n\nThings you know about this user from past sessions:\n"
                             + "\n".join(f"- {fact}" for fact in load_memory()))
another_fresh_agent = Agent(MODEL, system_prompt_with_memory, tools_schema, AVAILABLE_TOOLS)

Re-run the save cell and the fact is stored twice. Real memory systems need dedupe and retrieval, not just append.

Section 06·Policy

Same weights, different behavior

A policy is the behavior an agent follows. Part of it lives in the weights; the rest comes from the scaffolding and harness wrapped around them.

anatomy-of-ai-agent.ipynb§6
terse_agent = Agent(model=MODEL,
    system_prompt="You are a terse assistant. Answer in 5 words or fewer. No explanations.",
    tools_schema=tools_schema, available_tools=AVAILABLE_TOOLS)

verbose_agent = Agent(model=MODEL,
    system_prompt="You are a thorough, friendly assistant. Always explain your reasoning ...",
    tools_schema=tools_schema, available_tools=AVAILABLE_TOOLS)
"Should I bring an umbrella in Paris today?" · both called get_weather → 8.5C, overcast
terse_agentNo, it's just overcast.
verbose_agentTo give you the best advice, I checked the current weather for Paris. Right now, it is 8.5°C and overcast. … Because the weather can be unpredictable when it's cloudy, I would recommend bringing an umbrella just to be safe …

One line changed

Same model, same tools, same harness, same weather data. Only the system prompt differs.

Policy ≠ weights

Part of the behavior is learned in training. A lot of what feels like personality is scaffolding.

Policy ≠ agent

The agent is the machinery. The policy is how that machinery ends up behaving.

Section 6b·Reasoning

Thinking is a switch in the request

Same weights. Gemma 4 thinks when a <|think|> token opens the system prompt; OpenRouter's reasoning parameter adds it for you, per call.

anatomy-of-ai-agent.ipynb§6b
# inside Agent.run(): an OpenRouter field, so it rides in extra_body
if self.reasoning:
    kwargs["extra_body"] = {"reasoning": self.reasoning}

# "off" is explicit: some models think by default
no_think_agent = Agent(..., reasoning={"enabled": False})
think_agent    = Agent(..., reasoning={"enabled": True})

no_think_agent.run(reasoning_question)   # → 40   (no trace)
think_agent.run(reasoning_question)      # → 40

think_agent.last_reasoning   # the trace: message.reasoning,
                             # a separate field from .content

It costs something

More output tokens and more latency on every call that has it on.

Worth it for some questions

Here both got 40; the trace is the only difference. On harder problems, that trace is where accuracy comes from.

Showing it is a product call

The trace arrives in its own field. The harness decides whether the user ever sees it.

Section 07·Tool use

When a tool call fails

Bad arguments, unknown codes, a tool that doesn't exist. The harness turns the exception into a tool result, so the model reads its own mistake instead of crashing the run.

Agent.run(), the tool step§4 · §7
for tool_call in msg.tool_calls:
    fn_name = tool_call.function.name
    try:
        fn_args = json.loads(tool_call.function.arguments)
        result = self.available_tools[fn_name](**fn_args)
    except Exception as e:
        result = f"Error: {e}"   # errors become data

    self.messages.append({
        "role": "tool",
        "tool_call_id": tool_call.id,
        "name": fn_name,
        "content": str(result),
    })
error_agent.messages, saved run
userUse convert_currency to convert 100 USD to the currency code XYZ. Tell me what happens.
assistantconvert_currency({"from_currency":"USD", "to_currency":"XYZ", "amount":100})
toolError: HTTP Error 404: Not Found
assistantThe attempt to convert 100 USD to the currency code "XYZ" failed because "XYZ" is not a valid currency code, resulting in a 404 error.

Harness engineering is designing this layer: when to stop, how errors surface, and what the model gets to see.

Section 08·Skills

Instructions, loaded only when needed

A skill is reusable instructions, loaded on demand. A tool is code that runs. Version one is the simplest possible loader: a keyword router in Python.

anatomy-of-ai-agent.ipynb§8
SKILLS = {
    "trip_itinerary": {
        "description": "Formatting rules for multi-day trip itineraries.",
        "trigger_words": ["itinerary", "multi-day", "day trip", "day-by-day"],
        "instructions": "... one line per day, in the form 'Day N: <plan>'.",
    },
    "budget_note": {
        "description": "Rules for how to state amounts of money.",
        "trigger_words": ["budget", "cost", "price", "currency"],
        "instructions": "When money is discussed, always state the currency explicitly ...",
    },
}

def build_system_prompt(base_prompt, user_input, skills):
    prompt = base_prompt
    for name, skill in skills.items():
        if any(word in user_input.lower() for word in skill["trigger_words"]):
            prompt += f"\n\n[Skill: {name}]\n{skill['instructions']}"
    return prompt

"Give me a 3 day itinerary"

Matches itinerary. The prompt gains a [Skill: trip_itinerary] block.

"What's the weather in Tokyo?"

No trigger matches. The prompt stays exactly the base prompt.

Predictable, but not judgement

Python decides by keyword match. Real skill systems let the model decide. Next slide.

The Agent class doesn't change at all. budget_note pairs with convert_currency: the skill says how to phrase money, the tool supplies the number.

Section 08·Skills, the way real systems do it

Let the model decide which skill to load

The prompt carries only each skill's name and one-line description. A load_skill tool returns the full instructions when the model asks. Cheap index, full text only when used.

anatomy-of-ai-agent.ipynb§8
def load_skill(name: str) -> str:
    """Return a skill's full instructions. The model calls this when it decides it needs them."""
    if name not in SKILLS:
        return f"No skill named {name!r}. Available: {', '.join(SKILLS)}"
    return SKILLS[name]["instructions"]

skill_index = "\n".join(f"- {name}: {skill['description']}" for name, skill in SKILLS.items())
model_driven_prompt = (SYSTEM_PROMPT
    + "\n\nSkills you can load with load_skill before answering, if relevant:\n" + skill_index)

skill_choosing_agent = Agent(MODEL, model_driven_prompt,
    tools_schema + [load_skill_schema], {**AVAILABLE_TOOLS, "load_skill": load_skill})
skill_choosing_agent.run("Give me a 3 day itinerary for Tokyo.")
skill_choosing_agent.messages, saved run
assistantload_skill({"name": "trip_itinerary"})
toolWhen asked for a trip itinerary, format the answer as a numbered list, one line per day, in the form 'Day N: <plan>'. …
assistant1. Day 1: Explore the historic Senso-ji Temple in Asakusa, walk through Ueno Park, …
2. Day 2: …
3. Day 3: …

This is progressive disclosure, as in Anthropic's Agent Skills. Same Agent class, one more tool: the model chooses, the harness executes.

Section 09·Sub-agents

A tool that thinks for itself

A full, independent Agent with its own prompt, messages, and loop, handed to the orchestrator as if it were one more plain function.

anatomy-of-ai-agent.ipynb§9
packing_subagent = Agent(model=MODEL,
    system_prompt="You are a packing advice specialist. Given a weather description, "
                  "respond with ONE short sentence of packing advice. Nothing else.",
    tools_schema=[], available_tools={})

def delegate_to_packing_subagent(weather_description: str) -> str:
    return packing_subagent.run(weather_description)   # a whole harness loop

orchestrator_tools = tools_schema + [delegate_schema]
orchestrator_available_tools = {**AVAILABLE_TOOLS,
    "delegate_to_packing_subagent": delegate_to_packing_subagent}
orchestrator = Agent(MODEL, SYSTEM_PROMPT, orchestrator_tools, orchestrator_available_tools)
orchestrator.messages, saved run
assistantget_weather({"city":"New York"})
toolNow: 14.5C, overcast.
assistantdelegate_to_packing_subagent( {"weather_description": "overcast and 14.5C"})
toolPack a lightweight waterproof jacket and layers to stay warm and dry.

To the orchestrator, both calls look identical. A tool just runs code; a sub-agent reasons on its own first. The orchestrator only ever sees its final answer.

Section 11·Capstone

Solving Maya's Tokyo trip

Every tool, both skills, and the sub-agent, on the request from the start. Nothing new gets wired up here.

anatomy-of-ai-agent.ipynb§11
capstone_request = (
    "I'm flying to Tokyo in 3 days for work. Give me a day-by-day itinerary for the trip "
    "accounting for the weather, tell me what to pack, and convert my daily budget of "
    "$600 to Japanese yen.")

maya_prompt = build_system_prompt(SYSTEM_PROMPT, capstone_request, SKILLS)
maya_agent = Agent(MODEL, maya_prompt, orchestrator_tools,

Day 2: Visit shrines and gardens while enjoying the mostly clear weather.
